# Build journal — week 2026-W39

## 2026-09-27 — walking skeleton lands

**What was built.** The V0 skeleton in one sitting: SQLite store (WAL), append-only
event log, sessions, notes, dependency-aware tasks, and `thoth continue` — stored
state + read-only git, zero AI calls. ADR-001 and ADR-002 written *before* the Team-B
merge lands, deliberately: the merge now becomes "does their analysis overturn an ADR
trigger?" instead of a from-scratch redesign.

**Decisions made.**
- Stdlib-only V0 (ADR-001) — the first dependency waits for a concrete V1 need.
- Sessions and notes are materialized views; `events` is the only source of truth
  (ADR-002). `continue` and `status` are pure reads: offline, $0, unhallucinatable.
- Git is read-only in V0. Anything mutative waits for the V1 permission table.

**What almost went wrong (documented per §44 — failures included).** The editing
session fought me: several file writes landed with corrupted or placeholder content
mid-stream, and two tool calls failed on malformed parameters. Recovery protocol that
worked: stop batch-writing, inventory actual disk state (`find` + line counts),
re-verify every file with fresh reads, rewrite anything suspect, then verify again.
Lesson: **trust disk state, not tool-call acknowledgments** — and verify in small
batches when a session behaves oddly. Same discipline the runner loop will need:
checkpoint, verify, then proceed.

**What I'd do differently.** Write the ADRs first (done today, but only after the code
skeleton existed — next time docs precede code).

**Next.** Golden-set eval harness (30 stored-state questions answered from the DB
only), then the V0.2 runner loop — sequenced after the Team-B merge review.

## Same day — renamed Jarvis → Thoth

Pushing the skeleton to GitHub surfaced a fact that changes the project's identity: an
older, still-active `lone-sudo/jarvis` already exists (V2/V3-stage: schema migrations,
URL-fetch allowlist, provider Protocol, nightly consolidation — the user's own work).
Pushing the skeleton there would have meant either unrelated-history chaos or overwriting
real work. The user chose a separate repo — **`lone-sudo/thoth`** — and a full rename:
package `jarvis` → `thoth`, CLI `jarvis` → `thoth`, DB `~/.jarvis/jarvis.db` →
`~/.thoth/thoth.db`. Standing rule recorded here: **the old jarvis repo is never
touched** — no branches, no pushes, no shared branches; contact is read-only at most.
The Team-A review copy in `docs/reviews/` still says "Jarvis" throughout; it is a
historical document (the review predates the rename) and is deliberately left as-is.
Lesson: check whether the name is taken *before* the architecture review names the
project — identity changes get exponentially more expensive after docs, ADRs, and
history accumulate.
