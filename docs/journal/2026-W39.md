## Same day — V0.2 runner skeleton (ADR-003 implemented)

**What was built.** The loop: load context package → plan → act (one tool) → verify
(code, not model) → checkpoint `run.turn.*`, with max-turns/budget/deadline bounds
enforced by the runner and carried *inside* checkpoints so resume can't reset them.
Three level-0 tools behind a `ToolSpec` registry: `shell.read` (allowlist +
chaining-blocked), `file.read` (workspace-escape-proof via resolve+relative_to),
`memory.search` (FTS5 with syntax neutralization, superseded-notes filtered).
`NoopPlanner` keeps the whole thing AI-free and testable; the model planner implements
the `Planner` Protocol later. CLI gained `run start/status/execute/resume`; `continue`
now surfaces parked runs with their resume command. Schema migration v2 (runs + FTS
triggers + backfill) applied lazily on connect. 49 tests passing.

**What went wrong first.** First test run: 8 failures, one root cause —
`build_context` wrote three sections it never assigned (`task_state`), read a
nonexistent column via an unaliased join (`n.body`), and read `verify_ok` from turn
payloads that store `verify.ok`. Three bugs, one function, found only by the tests —
which is the point of the golden-set discipline the Team-A review keeps pushing.

**Design notes worth keeping.** Verify-failure parking (3 consecutive) means a
broken tool can't spin the loop forever. FTS-with-backfill means notes written
pre-migration are searchable without a rebuild command. The planner-retry
(`resume_run`) deliberately inherits bounds from the last checkpoint — a crash cannot
be exploited to reset a budget.

## Same day — ADR-004: the security choke point drafted

One ADR for the three fears that kept recurring (spend, privacy, injection) because
they share one shape: they're only real if a code path can act without a checkpoint.
The decision in a sentence: **every consequential crossing — outbound AI request,
network call, level-≥1 tool call, externally-sourced memory write — passes one
fail-closed guard whose every verdict is an event.** Injection defense is four
mechanical layers (taint at ingestion, content-as-data rendering, no privilege
crossing justified by content alone, floors that rise but never fall) with detection
heuristics demoted to review aids — the defense must work even when detection fails.
The ADR is honest about costs: taint bookkeeping will over-restrict some derived
notes until provenance-reviewed, and that's the cheap failure mode. Four questions
staged for Team-B, including the sharpest one: should `sensitive` data ever be
expressible to cloud providers under explicit operator override (current answer:
never — and it's worth stress-testing that absolutism).

## Same day — the golden set exists (30 questions, one real bug caught)

Built the V0 gate from the Team-A review: a deterministic seed world (two projects,
fixed timestamps, known sessions/tasks/notes/runs) and 30 checks that continue/
status/run must answer from the DB alone, zero AI calls. Two humbling findings:

1. **Designing the golden set caught a real bug before running anything:**
   `last_parked` correlated each run to the *latest park event overall*, not its own —
   so a park from project A could leak as project B's reason. Exactly the class of
   wrong-answer-that-looks-plausible the golden set exists to catch. Fixed with a
   correlated subquery on `json_extract(payload, '$.run_id')`.
2. **One of my 30 questions was wrong, not the code:** check 14 read `summary` from
   the sessions row, but summaries deliberately live in the event log (ADR-002).
   The DB wasn't lying; my question was. Worth recording: when a golden check
   fails, first ask whether the *expected answer* respects the storage design.

Also learned (again): seeding must respect the system's own invariants — you can't
add a task depending on an already-done dependency, because `tasks.add` rejects it.
The seed now completes the dependency *after* the child exists.

30/30 pass; pytest wrapper added so the gate runs in the normal suite. From now on:
run `python -m evals.run_golden` after every schema or surface change, weekly
regardless (Team-A §46.B).

## 2026-09-28 (later) — Qwen2.5-3B: the 3B proof and the summarizer finding

Goal: hint-free `--plain` run (no few-shot, no suggested plan) ending in a
self-driven `done`. Result: not achieved by the model — but the investigation
produced the session's most important architectural finding.

The download, documented for the record: ~2.1GB across seven resumable windows
(per-invocation `--max-time 45`, stall guards, loop with deadline), throttled
to 120–600KB/s throughout. Completed at exactly 2,104,932,768 bytes and
verified by sha256 against HuggingFace's LFS oid — bit-perfect. The windowed
resume loop is now the house pattern for big artifacts on this network.

Product fixes the 3B forced (all regression-tested, suite now 102):
- **Tool schemas in the prompt** — `_build_prompt` listed descriptions only; a
  capable model cannot guess undocumented required params (first plain run:
  right tool, missing `path`). Required args now render into the tool list.
- **History reaches the prompt** — decide() was throwing history away
  (ADR-003 §2's observation loop never reached the model). Rendered as
  "turn N: tool [ok] ...".
- **Bounded retry** — one malformed answer from a stochastic model killed the
  whole attempt; `_ATTEMPTS_PER_PROVIDER = 2` retries the same candidate (with
  `provider.retry` events) before falling through; structural failures never
  retry.
- **Repeat-breaker** — the model executed the same verified `file.read` four
  turns running (identical digests). The runner now parks on a repeat of a
  VERIFIED-OK idempotent action before executing it again. Scoping decisions:
  within-episode only (resume continuation is a designed pattern), failing
  repeats stay under 3-strikes verify (retrying flaky failures earns
  information), initialized fresh per invocation. Three new tests.
- **Output observations in checkpoints** — turns recorded digests only; the
  model can never feel done about an outcome it cannot read. Checkpoints now
  carry a 200-char observation (tool detail first, payload sample second).
- Driver: `--plain` mode with a strict gate (done AND >=1 verified turn),
  bounds coherence (execute_run overrides start_run), temp 0.4.

The finding that closes the investigation: replaying the exact post-turn
prompt with a SEMANTIC result line ("read README.md: 46 lines") made Qwen3B
finish instantly with a correct done plan. Raw-payload and detail-first
observation lines did not. The missing layer is deterministic per-tool result
summarization (file.read -> "read {path}: {detail}" class) between verify and
checkpoint — V2 build item, small, model-agnostic, no extra AI calls in V2.1.
Until then, `--plain` is the standing benchmark: it fails for exactly one
documented reason, and every park along the way was diagnostic, safe, and
cheap — propose -> validate -> refuse -> record -> park, now including the
repeat-breaker as a designed terminal state with a human-readable reason.

Also measured: 4x4 same-digest loop, max-turns override semantics (execute_run
bounds are the ceiling), and llama-server + Qwen2.5-3B quantization fit on the
ZBook (CPU inference, 2048 ctx, seconds-per-turn — viable for V1 budgets).

## 2026-09-28 (same evening) — ADR-005: the Telegram surface, designed

The parity track's item 4 gets its architecture before its code (the §45
discipline: design first, build small). The channel matrix decided itself:
Telegram's long-polling is the only candidate that is $0, operator-present,
requires no inbound port, and has inline decision buttons. Webhooks rejected
(a public URL is the inbound surface ADR-004's threat model exists to avoid);
email rejected (no card primitive, link-shaped phishing risk).

Three design claims made structural rather than conventional: (1) the surface
is a guarded crossing — `telegram.py` joins ollama.py as an I/O module under
the no-bypass scan, with an exact-host endpoint allowlist and token redaction
in the event log; (2) privacy ceiling at delivery — the render is the
redaction (PRIVATE -> counts, SENSITIVE -> withheld placeholder), so the V2
content formats inherit it for free; (3) no new permissions — zero ToolSpecs,
read-only chat pulls only, cards grant nothing by themselves (the approved
action still crosses the guard like any other). Cards resolve ADR-004 Open
Question 4: the interrupting channel exists and is pull-safe (timeout =
reject). V1.5 ships card plumbing with zero level>=1 tools — honest scope:
plumbing before need. Fourquestions staged for Team-B, including the card timeout horizon and whether
PRIVATE ever unlocks in chat (current: never).

## 2026-09-29 (same day) — the anti-hollow-finish floor, measured

The revisit trigger fired. Runner policy landed: **a done claim with zero
verified tool turns is refused** — `execute_run` parks the run with
`finish floor: done claimed with zero verified turns`, emits
`run.finish.refused` (with the claimed summary as evidence), and counts
verified turns ACROSS resumes (a run that acted in a prior episode can still
finish). Scripted no-work callers (the V0.2 CLI execute/resume planners) pass
`allow_finish_without_turns=True` explicitly — the floor is an
anti-hallucination guard, not a no-op policy. The finish-confirmation probe
needed no change: it only fires from the repeat-breaker, which requires a
prior verified turn by construction.

**Re-measure — same protocol, same models, floor on (canonical single run):**

| model         |  n |          json% |          tool% |         clean% |        finish% |
